# Lab harness

The harness runs the **Lab build** in libmgba from Bun. The **Viewer** shows one **Run** at a time in the browser. See `../CONTEXT.md` for the terms and `../docs/adr/` for the decisions.

## Run the Viewer

1. At the repo root: `make lab -j8`. This gives `pokefirered_modern_lab.gba` and its `.elf` with debug info.
2. In `lab/`: `bun install`, then `bun run viewer`.
3. Open http://localhost:8766. To use another port: `LAB_PORT=8767 bun run viewer`.

Requirements: Homebrew `mgba` (for `libmgba` and its headers), the macOS `dwarfdump`, and a C compiler. The harness compiles `shim/shim.c` into `.cache/` when the file changes.

## Run a Bot

In `lab/`: `bun run bot model`, or `bun run bot model full` for the `full` **Knowledge level** (the default is `player`). The command runs the **Bot** `bots/model.ts` headless from `saves/start.sav`, and prints each **Macro-action** with its result, its frame count and its texts. At the end, it prints the end reason of the **Run** (with the last text of the game at `unknown screen`), the **Milestones** and the party. The game is frozen at each **Decision point** (ADR 0002), so each start gives the same frames.

The lab has one **Bot**: `model`, the model bot (see "The model bot" below). Each new step of the story is added to the **Harness** and the model bot.

The scripted bot `starter` (`src/harness/scripted-bot.ts`) is a test tool, not a **Bot** of `bots/`: the **Viewer** and the Doc do not list it. The tests of the **Harness** use it because it is free and fast, and it always plays the same **Run**. It keeps its goal `first-rival-battle`, and it does not grow with the story. `bun run bot` runs only the **Bots** of `bots/`.

A **Bot** is `{ name, version, goal?, play(harness) }`, and optionally `frameBudget` (its frame budget when the Run gives none) and `model` (a model bot: its AI model and the options). A **Bot** with no `goal` plays to the last **Milestone** (`badge-8`). A module in `bots/` exports a **Bot** by default, or it exports `modelBot(model)`, a function that makes a model bot. `loadBot(name, model)` loads the module `bots/<name>.ts`, or the module at `name` when `name` is an absolute path (the tests load the scripted bot so). It calls `modelBot` with the model and the options of the **Run** (the missing options take their defaults), and refuses a model for a module with no `modelBot`. A **Bot** calls the harness with `await`, for example `await harness.goTo(10, 2)`. `must(result)` stops the Bot with an error when a result is not `done`.

`harness.play(bot)` plays a **Run** and gives its result: the end reason, the frames and the **Raw inputs** from the start of `play`, and the **Milestones**. A `Harness` object plays one Run: a second `play` is an error. `harness.close()` closes its emulator. `Harness.open(options, run)` can also take a `Run` that the caller opened: the Harness then owns it, and closes it when the Run cannot start. The end reason is one of:

- `goal`: the game reaches the **Milestone** `goal` of the Bot, or `badge-8` for a Bot with no `goal`. The **Macro-action** that reaches it does not return to the Bot.
- `bot stopped`: `play` of the Bot returns, or throws an error. In the second case, `harness.play` keeps the result for the Run record, then throws the error again.
- `user stop`: a person stopped the Run (`Harness.open({ stopAsked })`: a function that gives `true` to stop). The Run ends after the **Macro-action**, the **Raw input** or the **Model call** that plays: that action or call does not return to the Bot, but it is in the Run record.
- `cost limit`: the **Model calls** of the Run cost more than the cost limit of its model bot (`bot.model.costLimit`). The Run ends after that **Model call**: the call does not return to the Bot, but it is in the Run record. It is a normal end, not an error.
- `frame budget`: the Run used its frame budget, from the start of `play`: the `frameBudget` of `Harness.open`, else the `frameBudget` of the Bot (`starter`: 30 000 frames). With neither, the Run has no frame budget. The Run stops at the last frame of the budget, also inside a **Macro-action**: that action does not return, and it is not in `harness.actions` or in the events of the Run record.
- `no progress`: the stuck counter reached N (`Harness.open({ noProgressLimit: N })`). With no `noProgressLimit`, the Run has no such limit, but the Harness still counts. While a **Bot** plays, `harness.noProgress` gives the count (`stuck`) and `since`, the number of events of the Run at the last progress.
  - The stuck counter: each **Macro-action** and **Raw input** that ends at a **Decision point** adds 1, also when it is `impossible` with no frames, and also in a battle. An action that ends at a text or at a busy game adds nothing: the `readText` after it ends at the **Decision point**. Progress makes the counter 0 again.
  - Progress: a new map, a new **Milestone**, a new exit in the **Atlas** (a warp or an edge that the player saw or took for the first time), a level up of a Pokémon of the party, or a new text of a person. A text that the player heard before from the same person is not progress. A new cell is not progress.
- `whiteout`: all the Pokémon of the party fainted, in a battle or out of a battle (poison), and the model bot has the option `stopAtWhiteout` (`bot.model.stopAtWhiteout`). The Harness reads the whiteout from the game state (`gMain.callback2` is `CB2_WhiteOut`), not from the text. The Run ends after the **Macro-action** or the **Raw input** of the whiteout: usually the `readText` that reads the texts to the walk in the Pokémon Center. That action does not return to the Bot, but it is in the Run record with its texts.
- `unknown screen`: the Bot calls `harness.end("unknown screen")` at a screen that it cannot play. The result also has `lastText`: the last text of the game in the results of the actions.

For `goal`, `user stop`, `cost limit`, `frame budget`, `no progress`, `whiteout` and `unknown screen`, the **Macro-action**, the **Raw input** or the **Model call** throws an error that ends the Run: the Bot must not catch the errors of the harness.

`goTo(x, y, map?)` walks to a cell of the player's map, or of the map with the name `map`, for example `goTo(12, 3, "PalletTown")`. The route goes through warps, map edges and ledges (only in their jump direction). People are obstacles: the player waits for them. A fixed obstacle is a blocked cell (see "Fixed obstacles"). The player takes a stair or arrow warp when it stands on the cell and pushes toward its direction, and a door when it pushes north from the cell below. With no `map`, the cell can also be an exit of the player's map: a warp that the player can take (a door, stairs, an arrow warp), or the cell just past an edge with a neighbour map, for example `goTo(12, -1)` for the north edge. Then `goTo` takes that exit, and it is `done` when the player arrives on the other map. The result is one of:

- `done`: the player is on the cell.
- `impossible`: the cell is outside its map (the reason gives the cells of the map, and tells when no map connects to the edge that a cell just past it would cross, when the edge is water: "you cannot go there now: the south edge of PalletTown is water. Only a Pokémon that knows SURF can cross water, and you have none", or when the cell past the edge leads to a cell of the next map where the player cannot stand: "cross the <side> edge at another cell"); a fixed obstacle closes the only way (see "Fixed obstacles"); there is no route, even with no people on the maps; or the player cannot walk now; or the player does not move and no person is in the way; or a warp does not start. When `goTo` finds this before the first move, no frames run.
- `blocked`: a person stays in the way. `goTo` waits and computes the route again; it stops when a person stops the player three times on the same cell.
- `interrupted`: the game stopped the walk, with the reason `trigger` (coord trigger), `trainer` (a trainer sees the player), `script` (another script), `battle` (a wild battle starts) or `map` (the player arrived on a map that is not on the route). `goTo` stops at the first frame of the interruption and does nothing more. For `map`, that frame is when the warp ends.

`interact(x, y)` turns the player to the cell next to it and presses A, for example on a person, a sign or the Poké Ball on a table. Then it runs the game to the next Decision point. It is `impossible` when the game does not wait for the player to walk or when the cell is not next to the player (in these two cases, no frames run), when the player does not turn or walks when it turns, or when nothing on the cell starts a script. While the player turns, the game can interrupt `interact` as it interrupts `goTo`.

`availableActions()` gives the **Macro-actions** that the game accepts now:

- When the game waits for the player to walk: `{ name: "goTo" }` (the Bot chooses the cell), `{ name: "swap" }` with 2 Pokémon or more in the party (the Bot chooses them), `{ name: "use", item }` for each item of the Bag that works outside a battle (the Bot chooses the Pokémon for an item that works on a Pokémon), and `{ name: "interact", x, y }` for each cell next to the player with a person or a sign. A sign that is read from one side only is in the list only when the player is on that side. Bookshelves, PCs on a metatile, water and the people behind a counter are not in the list yet, but `interact` works on them.
- At a choice: `{ name: "choose", option }` for each option.
- At the battle action menu: `{ name: "fight", move }` for each move with PP, `{ name: "switch", slot }` for each Pokémon of the party with HP that is not in the battle, `{ name: "run" }` in a wild battle, and `{ name: "use", item }` for each item of the Bag that works now (the Bot chooses the Pokémon). At the move menu: the same `fight` entries.
- In the party menu of a battle: `{ name: "send", slot }` for each Pokémon of the party with HP that is not in the battle.
- At the shop menu of a Poké Mart and at its buy list: `{ name: "buy", item }` for each item for sale, `{ name: "sell", item }` for each item of the Bag that the shop buys (the Bot chooses the quantity), and `{ name: "leave" }`.
- At the naming screen: `{ name: "name" }` (the Bot chooses the text).
- At a text, or when the game is busy: `{ name: "readText" }`. The harness cannot tell a busy game from a menu that it does not know (the PC): there, `readText` is `impossible` after 3600 frames.

A **Macro-action** that the game does not accept now (for the kind of `waitingFor`) returns `impossible`, and no frames run. `interact` runs at each walk Decision point, also when the list has no `interact` entry. The list does not check the elevation of a person or a sign, or a person who is invisible or has no script; no such case is on the path to the starter.

`observe()` gives what the game waits for, the party, the **Milestones** and the **Atlas** (see "The Atlas" below). At the naming screen, it gives `mode: "naming"` and nothing more, also in a battle. On the overworld (`mode: "overworld"`), it also gives the map, the player, the grid of the map and `people`: each person of the map with its `localId`, its cell, `loaded` (the game has it in memory now, near the screen) and its sprite (`graphics`, the name of `OBJ_EVENT_GFX_*` without the prefix, for example `PROF_OAK` or `ITEM_BALL` for a Poké Ball on a table). A fixed obstacle is not in `people`: its cell is a blocked cell of `grid` (see "Fixed obstacles"). In a battle (`mode: "battle"`), it gives `battle` with the kind (`trainer` or `wild`) and two Pokémon. The player's Pokémon has `partyIndex` (its place in `party`), its species, nickname, the types of its species, level, HP, status and moves. It also has its battle stats `attack`, `defense`, `speed`, `spAttack` and `spDefense`, and `statStages` from -6 to 6 for these stats, `accuracy` and `evasion`. The enemy Pokémon is as the player sees it: species, the types of its species, level, `hpPercent` (the HP bar, 48 pixels, as a percentage), status, `statStages` and `movesSeen`. `movesSeen` has the moves that the game announced for this enemy Pokémon in this battle, for example "Foe BULBASAUR used GROWL!". At the `full` **Knowledge level**, the enemy also has `exact`: its `hp`, `maxHp` and `stats`. The volatile states (for example confusion), the ability and the held item are not in the battle state yet. Open the harness with `Harness.open({ knowledge: "full" })`.

The party is in the order of the party menu out of a battle, also while the party menu of a battle is open: there, the game shows the Pokémon in the battle first. Each Pokémon of the party has what the Summary screen shows: its species, nickname, `types`, `ability` (the name and the description), `heldItem` (`null` for none), `nature`, level, `exp` and `expToNextLevel` (0 at level 100), HP, status (`none`, `sleep`, `poison` (also for toxic poison), `burn`, `freeze` or `paralysis`; a Pokémon with 0 HP keeps its status), `stats` (`attack`, `defense`, `speed`, `spAttack`, `spDefense`) and moves. Each move has its name, `type`, `power` and `accuracy` (`null` where the Summary screen shows "---": a power below 2, an accuracy of 0), its PP now and its maximum PP, and its `description` on one line. The IVs and the EVs are not in it: the Summary screen does not show them. `bag` has the pockets with items, in the order of the Bag screen (`ITEMS`, `KEY ITEMS`, `POKé BALLS`, `TM CASE`, `BERRY POUCH`): each item has its name, `quantity`, `description` (its effect, as the Bag screen shows it), `price` (the price of one item in a Poké Mart; 0 for the Key Items) and `battle`: `pokemon` (it works on a Pokémon of the party, for example a Potion), `alone` (for example a Poké Ball or an X item), or `null` (it does not work in a battle). `walk` is the same outside a battle: `pokemon` for a medicine of the `ITEMS` pocket (for example a Potion, an Antidote or a Revive), `alone` for REPEL, SUPER REPEL, MAX REPEL and ESCAPE ROPE, else `null` (the other items open other screens: not covered yet). `money` is the money of the player. The **Milestones** are the story steps reached, in story order: `has-pokemon`, `first-rival-battle` (the rival leaves the lab after the first battle, won or lost), `pokedex` (Oak gives the Pokédex for OAK'S PARCEL) and `badge-1` to `badge-8`. The text of `pokedex` in the prompt is "Get OAK'S PARCEL in Viridian City and bring it back to Professor Oak."

### The Atlas

`observe().atlas` is the **Atlas** of the **Run**: `maps`, one entry for each map that the player visited, in the order of the first visit. The Harness makes it from the frames of the Run (`src/harness/atlas.ts`). Each map has its name, its `width` and `height`, and:

- `cells`: one character for each cell, row by row, as `MapGrid.kinds` (from the ROM, with the cell of each fixed obstacle as `#`), and `?` for a cell that the player did not see. The player sees the 15 × 10 cells of the screen: 7 cells to the left and to the right, 5 cells up and 4 cells down. The cells of a neighbour map that the screen shows past an edge are not in the Atlas.
- `warps`: the exits of the map (doors, stairs, exit mats) that the player saw or took, with their cell, their metatile `behavior` and `to`. `to` is the map where the exit goes when the **Run** went through it, else `null`. An exit goes in the two directions, so the Harness also knows the destination of the exit where the player arrives on a map: after the starter **Run**, the door of the player's house in Pallet Town has its destination, but the door of the rival's house has none.
- `edges`: the edges of the map with a neighbour map, when the player saw a cell of that edge or crossed it, with `side` and `to`, as for the warps. A blocked edge also has `blocked: "water"`: no cell of the edge leads on foot to a cell of the next map, and water is in the way (for example the south edge of Pallet Town, to Route 21). Only SURF crosses it, and the Harness cannot surf. Thus the text says "you have none" also when a Pokémon of the party knows SURF.
- `signs`: the signs on the cells that the player saw, with `text`: the text of the `readText` just after an `interact` with the sign, else `null`.
- `hasEdges`: an edge of the map goes to another map, seen or not. A building has none.
- `people`: the people that the player saw on the screen, with their `localId`, `graphics`, the last cell where the player saw them, and `texts`. A person with the sprite of the rival (`BLUE`) also has `rival`: the name of the rival in the save, for example `BOB`. The game gives this name to the player at the start, and calls the rival by it. A talk is a done `interact` with a person (or with a counter that has a person behind it), and its text is the text of all the `readText` after it. The **Atlas** keeps each different text of a person once, in order. The key of a person is its map and its `localId`, so a person keeps its texts when it moves.
- `obstacles`: the fixed obstacles that the player saw on the screen, with their cell, `name` and `move`. The **Atlas** keeps an obstacle that it saw.
- `entry`: a cell of the map where the player stood and can walk, for a `goTo` to this map.

`atlas.lastTalk` is the person of the last talk of the **Run**: its map and its `localId`, or `null`.

At the `full` **Knowledge level**, the Atlas has all the maps of the game from the ROM: all the cells, all the exits and edges with their destination, and all the signs and people (with the texts that the player read and heard). The cell of each fixed obstacle is `#`, but `obstacles` has only those that the player saw. The `entry` of a map that the player did not visit is a walkable cell next to one of its warps, else a walkable cell on one of its edges with a neighbour map. Its first `observe()` reads the 425 maps (about 30 ms).

`harness.sight()` gives what the player really saw, also at the `full` level: for each visited map, one character for each cell, `1` seen and `0` not seen. The Viewer shows the other cells in grey.

`observe().waitingFor` tells what the game waits for now. `harness.waitingFor()` gives the same value, also when `observe()` cannot read the game (for example in a fade between two maps, where `observe()` throws an error):

- `{ kind: "walk" }`: the player can walk.
- `{ kind: "text" }`: a text box waits for A.
- `{ kind: "choice", options, cursor }`: a yes/no, for example `["YES", "NO"]` with the cursor on 0. In a battle, the yes/no of the battle scripts is also a choice, for example "Use next POKéMON?" after a faint in a wild battle, or the nickname after a catch.
- `{ kind: "naming", subject, maxLength, keys }`: the naming screen. `subject` tells what it names, for example `"a nickname for BULBASAUR"`, `maxLength` is the maximum number of characters (10 for a Pokémon), and `keys` are the characters of the keyboard (all the pages, each one once). YES at a nickname question opens it, also after a catch.
- `{ kind: "battleAction" }`: the battle menu FIGHT, BAG, POKéMON, RUN.
- `{ kind: "battleMove" }`: the move menu of the battle.
- `{ kind: "partyPick" }`: the party menu of a battle waits for a Pokémon.
- `{ kind: "shopMenu", items, screen }`: a Poké Mart. `items` are the items for sale, each with its `name` and its `price` for one item. `screen` is `"menu"` for the shop menu (BUY, SELL, SEE YA!), where the game sets the items before it shows the menu, or `"buyList"` for the buy list. The **Macro-actions** of the Poké Mart end at the shop menu, so the game stops in the buy list only after an Interruption or a **Raw input**. `observe()` gives the overworld there: the list shows the map behind it.
- `{ kind: "busy" }`: the game waits for no input. For example, a text prints, people walk or the screen fades.

In a battle, `text` is also the level-up stats box, the texts of Oak in the party menu of the first battle, and the Pokédex page of a Pokémon caught for the first time.

A text box that closes by itself is not a `text` Decision point. On the frame of a map arrival, the game can show `busy` while a frame script of the map starts, for example in Oak's lab.

`readText()` reads the texts of the game. It runs the game until a text waits for A. Then it presses A at each `text` Decision point, until the text box closes or a choice shows. Then it runs the game to the next Decision point. Its result has `text`: one plain string for each message. Line and page breaks become spaces. The result also has the messages that closed by themselves. A text that waits for A after the box closed is not in the result: the next `readText()` reads it. The result is `impossible` when the game waits for the player to walk, shows a choice, a battle menu, the shop menu or the naming screen, and `interrupted` with `battle` when a battle starts. In a battle, `readText` reads the battle messages and the texts of Oak (the first battle is a tutorial), and stops at the next battle menu. At the end of a battle, it stops at the first text of the overworld: the next `readText` reads it. A whiteout is different: when all the party faints, in a battle or from the poison on a walk, `readText` reads the texts of the whiteout, runs the game through the fade and the warp, and reads the texts in the Pokémon Center (or in the house of the player before the first Pokémon Center), to the walk there. In the party menu of a battle, it presses A at the texts of Oak but does not read them.

`fight(move)` uses the move `move` (0 to 3, the order of `battle.player.moves`): from the battle action menu it moves the cursor to FIGHT and presses A, then it moves the cursor to the move and presses A, and runs the game to the next Decision point. Its result has `text`: the messages of the turn, for example "SQUIRTLE used TACKLE!". A message that waits for A at the end is not in it: the next `readText()` reads it. `fight` is `impossible`, with no frames, when the Pokémon has no such move or the move has no PP. When no move has PP, the game uses Struggle from FIGHT, but no Macro-action selects it yet: use **Raw inputs**.

`run()` selects RUN in a wild battle, with the messages of the turn as `fight`. Against a trainer, it is `impossible`, with no frames.

`switch(slot)` selects POKéMON at the battle action menu, then the Pokémon `slot` (its place in `observe().party`) and SHIFT in the party menu. Its result has the messages of the turn, as `fight`. `send(slot)` does the same in the party menu of a battle, for example after a faint: it selects the Pokémon and SEND OUT. When the game refuses the Pokémon (it has no HP, it is already in the battle, it cannot leave the battle), the result is `impossible` with the text of the game as its reason, for example "SQUIRTLE is already in battle!", and the game waits again for the same Decision point. They are `impossible`, with no frames, when the party has no Pokémon `slot`.

`swap(first, second)` opens the Start menu on a walk, selects POKéMON, then the Pokémon `first`, SWITCH and the Pokémon `second`, and closes the menus: the two Pokémon change their places in the party. It is `impossible`, with no frames, when the party has no such Pokémon or when `first` and `second` are the same. The party menu and the Start menu read the input only on some frames: these **Macro-actions** press a button for as many frames as the game needs to read it.

`use(item, on?)` uses an item of the Bag in a battle, for example `use("POKé BALL")` or `use("POTION", 0)`. `item` is the name of the item as `observe().bag` gives it, and `on` is the index of the Pokémon in `observe().party`, only for an item that works on a Pokémon. It selects BAG, goes to the pocket and to the item, selects USE, then the Pokémon in the party menu. Its result has `text`: for an item on a Pokémon, first the message of the party menu (for example "SQUIRTLE's HP was restored by 3 point(s)."), then the messages of the turn, as `fight`. A Poké Ball is thrown in a wild battle: when the Pokémon is caught, `readText()` reads the messages and the Pokédex page, then the game asks for a nickname (a `choice`); after NO, or after YES and `name`, the Pokémon joins the party, or goes to the PC when the party is full. `use` is `impossible` with no frames when the Bag has no such item in its first three pockets (the Bag of a battle does not open the TM Case or the Berry Pouch), when the item does not work in a battle, for a Poké Ball in a trainer battle, when `on` is missing for an item that works on a Pokémon or is given for another item, and for an Ether (it asks for a move: not covered yet). When the game refuses the item, for example a Potion on a Pokémon with full HP, `use` closes the Bag and is `impossible` with the message of the game: "the game refuses the POTION: It won't have any effect.". The Bag keeps the item.

`buy(item, quantity)`, `sell(item, quantity)` and `leave()` work at the shop menu of a Poké Mart, and also at its buy list. Talk to the clerk across the counter with `interact`: the game then waits at the shop menu. `buy` selects BUY, the item in the list, the quantity and YES, then returns to the shop menu: the Bag gets the items and the money goes down by their price. `sell` selects SELL, the item in the Bag and the quantity, selects YES, then returns to the shop menu: the Bag loses the items and the money goes up by half of their price. `leave` selects SEE YA! and reads the texts of the clerk ("Please come again!") until the walk: its result has `text`, as `readText`. `buy` is `impossible`, with no frames, when the list has no such item, when the money does not pay all the items (for example "20 POKé BALL cost 4000 and the money is 3080"), or for a quantity that is not 1 to 99. `sell` is `impossible`, with no frames, when the Bag has no such item, when the shop does not buy it (it has no price, as the Key Items), for an item of the TM Case or of the Berry Pouch (not covered yet), or for a quantity that is not 1 to the quantity in the Bag (99 at most). When the game refuses a buy or a sale, for example a buy with a full Bag, the result is `impossible` with the message of the game, and the game is at the shop menu again.
On a walk, `use(item, on)` opens the Start menu, selects BAG, the item, USE and the Pokémon, then closes the Bag and the Start menu. Only an item with a `walk` use works there: else `use` is `impossible` with no frames ("POKé BALL does not work outside a battle"). The game first shows the item on the Pokémon, then the party menu tells the effect: the result has this message in `text`, for example "SQUIRTLE's HP was restored by 3 point(s).". When the game refuses the item, `use` is `impossible` with the message of the game, as in a battle. A REPEL item and ESCAPE ROPE work alone: `use("REPEL")` selects USE, the game shows its text in the Bag ("PLOK used the REPEL."), and `use` closes the Bag and the Start menu. ESCAPE ROPE closes the Bag, the game shows its text on the field, and the player goes to another map: `use` ends at the walk on that map. The game refuses a REPEL while an earlier one still works ("But the effects of a REPEL lingered from earlier.") and ESCAPE ROPE outside a cave or a dungeon ("OAK: PLOK! This isn't the time to use that!").

`choose(option)` moves the cursor of the choice to the option (for example `"NO"`), in a grid menu left or right and then up or down, presses A, and runs the game to the next Decision point. It is `impossible` when the game shows no choice or when the choice has no such option.

`name(text)` types `text` on the naming screen, then selects OK. For each character, it changes the page of the keyboard with Select (uppercase, lowercase, symbols), moves the cursor with the input of the slow menus, and presses A. Then Start moves the cursor to OK, and A ends the screen. Then it reads the texts until the next Decision point: its result has `text`, as `readText`. `name("")` keeps the name of the game: the game does not copy an empty text. The keyboard has the letters, the digits, the space and `. , ! ? ♂ ♀ / - … “ ” ‘ '`. An ASCII `"` is “ and the next one is ”. `name` is `impossible`, with no frames, for a character that is not on the keyboard or for a text longer than `maxLength`.

`press(button)` is a **Raw input**: one press of a button (`"A"`, `"Up"`...), then the game runs to the next Decision point. The harness counts them in `rawInputs`, and `bun run bot` prints the count at the end.

`perform(action)` runs any **Macro-action** or **Raw input** from its description, for example `{ name: "goTo", x: 6, y: 1 }`: the model bot plays the action of its AI model through it.

After its A press, `interact` stops only for a battle (`interrupted` with `battle`), as `readText`, `choose` and `press` do, because a script runs during them. ## The model bot

The model bot (`bots/model.ts`, version 8, no goal) asks an AI model on OpenRouter what to do, and its code calls the harness (ADR 0003). One **Bot** plays all the models: the **Run** gives the model and its options.

1. Make an OpenRouter key for the lab only, with a credit limit in the OpenRouter dashboard. Put it in `lab/.env`: `OPENROUTER_API_KEY=sk-or-...`. Git ignores this file, and the key is not in the Run records or in the logs.
2. In `lab/`: `bun run bot model`, or `bun run bot model <id>` for another model, for example `bun run bot model deepseek/deepseek-v4-flash-0731`. The default model is `deepseek/deepseek-v4-flash`. The options are `--cost-limit <dollars>`, `--reasoning off|low|medium|high`, `--temperature <0 to 2>` and `--starter free|BULBASAUR|CHARMANDER|SQUIRTLE`, `--no-stop-at-whiteout` to continue the **Run** after a whiteout, and `--continue <Run record>` to continue a stopped **Run** (see "Continue a Run"). The Viewer also starts it (panel "Runs").

Only the models with structured outputs play: the request asks for a strict JSON schema and accepts only the providers that apply it (`provider.require_parameters`). The default reasoning is `low`: with `--reasoning off`, the request sends the effort `none`, so the model does not reason. It is cheaper, but a model with no reasoning makes more mistakes, for example a target letter that is not the target of its reason. A model that always reasons (for example `z-ai/glm-5.3-flash` or `openai/gpt-oss-120b`) does not have the effort `none`: do not give it `--reasoning off`. With no `--temperature`, the model uses its own default.

The code reads the texts (`readText`) and waits while the game is busy, with no **Model call**. It makes a **Model call** only when the game waits for a walk, a choice, a battle action or a move, a Pokémon in the party menu of a battle, or a name at the naming screen. When `readText` is `impossible` (a screen that no **Macro-action** covers), the code presses B 3 times, and the history of the model tells it. After 3 such screens in a row with no **Decision point** between them, the **Run** ends with `unknown screen` and the last text of the game.

The prompt is in English, and its size has a limit, also in a long **Run**. The parts that change little come first, so that the providers cache more of the prompt: the rules, then the **Milestones**, the **Mission** and the top nodes of the **Memory tree**, then the facts that change at each call:

- the rules of the program, the long-term goal ("Become the Champion: earn the 8 gym badges, then beat the Elite Four.") and the starter: the first Pokémon that the model must choose, or with `free` (the default), a sentence that tells it to choose the one that it likes. With the option `stopAtWhiteout`, the rules also say: "If all your Pokémon faint, the Run ends." The rules have no goal of the **Run** and no step of the story. They give the advice of a good player: talk to the people, heal at a Pokémon Center, train before a Gym Leader, buy Poké Balls and Potions. One paragraph tells the model to try something new when its last decisions give nothing new: talk to the people, read the signs, take the exits that it did not take, go to the cells that it did not see. The rules also tell what the extract of the **Atlas** is. The legend of the map is in the extract.
- the **Milestones**, the next **Milestone**: the first one, in the order of the story, that the **Run** did not reach, with a name and a place only (for example "Next Milestone: Earn the Boulder Badge from Brock, the Gym Leader of Pewter City."), and the last **Mission** that the model gave with the number of decisions since it changed ("Mission: Get my first Pokémon (the same for 12 decisions).");
- the top nodes of the **Memory tree** (`src/model/memory-tree.ts`), for example `#1-8: <summary>`, `#9-12: <summary>`, `#13: <note>` after 13 notes (see below);
- what the game waits for. At a choice, the line shows the question of the game and the options: `The game asks: "Do you want to give a nickname to this BULBASAUR?" Choose YES or NO.` The question is the last text that the game showed: a `zoom` or a `viewAtlas` does not hide it. With no such text, the line is `The game waits for a choice: YES, NO.`;
- the last **Objective** that the model gave, and the stuck counter (see "The stuck counter and the reflection turn"); in a reflection turn, the reflection instruction;
- the tries since the last progress: each **Macro-action** or **Raw input** that the code played for an answer of the model, one time, with the number of times, its result and the texts that the code read after it, for example `interact(9, 4) ×3: "Those are POKé BALLS. They contain POKéMON!"`. The code makes this list from the events of the **Run**, not from the answers of the model. The `readText` and the B presses of the code are not tries. The list keeps the last 20 lines, after one line with the number of the older tries, and each result has 200 characters at most;
- the last 15 **Model calls**: each answer, then the **Macro-actions** and **Raw inputs** that the code played, their results, the texts and the map changes, until the next **Model call** (30 lines at most for each);
- the important events since the last **Model call**, and the request to write a note (see "The events that ask for a note");
- the party with what the Summary screen shows (see `observe()`), the money, and the Bag once with the effect of each item (for example `- ITEMS: POTION ×5 (A spray-type wound medicine. It restores the HP of one POKéMON by 20 points.)`);
- at a walk, the extract of the **Atlas** (`src/model/extract.ts`). The layout comes from a reading test of 4 layouts (issue #24). First the map of the player, with its ranges ("x from 0 to 12, y from 0 to 9") and a legend. Then a grid of all the rows of the map. Each row starts with its y (`y= 2  #.....@...A##`), and the x header has the same width as this start. `?` is a cell that the player did not see. The targets are letters in the grid, so a digit is always a coordinate (a target after Z is `*`). Then the edges that go to another map, each with the `goTo` that crosses it. A blocked edge has the reason of the Harness in place of the `goTo`, and it is not a target. With no such edge, the extract says "no edge of this map leads to another map", or "no edge that you saw" when the map has edges. Then what the people of this map said to the player, one line for each person with all its texts. Then the fixed obstacles of this map, one line for each, with its move and no letter: "- CUT TREE at (11, 24). Only a Pokémon that knows CUT can remove it." Their cell is `#` in the grid. Then one line for each map one exit away, told from this map: "A (stairs) leads to PalletTown_PlayersHouse_2F. Its exits (cells of PalletTown_PlayersHouse_2F): …". Then the targets, in groups, the nearest first in each group. Each target has its distance and direction from the player in cells, not a path length: "2 south, 2 east", "adjacent north, you face it", "you stand on it".
  - "Exits of this map": the exits and the edges, with the destination and "taken" when the **Run** went through them, else "not taken". An exit can go to another map only when it is not taken, or when its destination has another exit. When no exit can go to another map, the line "No exit to the outside is seen yet: explore B." names the unseen cells;
  - "Unseen cells": the edges of the seen area, for example "unseen cells north of (6, 3)". For each side, it is the nearest seen cell that the player can reach on foot, next to a cell that the player did not see;
  - "People and signs": the people of the **Atlas** on this map at the cell where the player last saw them, with their sprite, the rival with its name ("BOB (your rival)"), "behind a counter: go talks across it" (a counter is next to the person, and the player can reach the cell after it) and "talked" with the last text of the person in quotes, for example `talked, "I see! BULBASAUR is your choice. …"`; the signs, with "read" and their text when the player read them. A person that the game hides now (an item ball that the player took) is not a target;
  - "Far maps": the other maps of the **Atlas**, for example "PalletTown_RivalsHouse, 2 exits away".

  The local part of the extract (the grid, the targets of the map, and the texts of its people and signs) is never cut and is out of the budget. The other maps (the lines of the maps one exit away and the targets of the other maps) have a budget of 1 500 characters, nearest first: past it, the maps that are far (in number of exits that the **Run** knows) lose their line first. Thus a large town does not remove its neighbours. The actions are `go <letter>`, `goTo <x> <y> [<map>]`, `viewAtlas`, `zoom <a-b>` and `press <button>`. A number in `go` is an answer that the Bot cannot read. For `go <letter>`, the code takes an exit, or walks next to a person or a sign and calls `interact` (for a person behind a counter, it walks to the front of the counter and calls `interact` on the counter, as the game lets a player talk across a counter), or calls `goTo` to the cell of the target or to the `entry` of another map. A person can move while the player walks to it: after the walk, the code reads the cell of the person again, and walks to it again two times at most;
- in a reflection turn, at a walk: the full **Atlas** after the extract;
- `viewAtlas` (not in a reflection turn): the code calls the model again at once, in the same conversation (see below). The new user message has the full **Atlas**: the other maps in detail, the nearest first. Each map shows the texts of its signs and people, and its fixed obstacles. Past 100 000 characters, each far map has one line (its exits, and the texts of its signs and people), so the full **Atlas** loses no map. No frames run. `viewAtlas` is not a **Macro-action**, and the model can use it one time at most in a conversation: a second `viewAtlas` is an answer that the Bot cannot read;
- `zoom <a-b>`, at each **Decision point**: the code calls the model again at once, in the same conversation. The new user message has the two halves of the node `#a-b` ("Node #1-8, its two halves:"), or tells that the range is not a node with two halves. No frames run. The model can zoom again to go down to the notes;
- at a choice: the map of the player (the same grid as at a walk, with no targets), or the battle for a choice in a battle, and `choose <option>`. There is no `press` at a choice, in and out of a battle. In a battle: the player's Pokémon (HP, status, stats, stat stages), the enemy as the player sees it with its types, and `fight <n>` for each move with its type, power, accuracy and PP, `switch <Pokémon>` with the Pokémon that can go into the battle, `run`, and one line `use <item> [on <Pokémon>]` with the names of the items that work now (an item name that is not in this list is an answer that the Bot cannot read). In the party menu of a battle: the battle, and `send <Pokémon>` with the Pokémon that can go into the battle. At a walk with 2 Pokémon or more: `swap <Pokémon> <Pokémon>`. At a walk: the `use` line with the items that work outside a battle: a medicine on a Pokémon, and REPEL, SUPER REPEL, MAX REPEL and ESCAPE ROPE alone (`use REPEL`). At the shop menu of a Poké Mart (also at its buy list, after a **Raw input**): the items for sale with the price of one item, the items of the Bag that the Mart buys with their quantity and the money for one item, and `buy <item> <quantity>` (an item for sale), `sell <item> <quantity>` (an item that the Mart buys; no line when the Bag has none) and `leave` (SEE YA!, then the walk). There is no `press` there: the code does all the menus of the Mart, and after a `buy` or a `sell` the model gets a new **Model call** at the shop menu. An item that is not in these lists is an answer that the Bot cannot read; the money and the quantities are for the **Harness** to check. A `<Pokémon>` is a nickname of the party (in any case) or a place in the party (1 is the first). A name that is not in the party is an answer that the Bot cannot read.
- at the naming screen: what the screen names and the maximum length (`The naming screen asks for a nickname for BULBASAUR, 10 characters at most.`), `name <text>` with the keys that the Harness reads on the keyboard, and `name` to keep the name of the game. There is no `press` there. The model is free to give a nickname or not.
- `press <button>` has no Start: the model bot does not know the Start menu. A `press Start` answer is an answer that the Bot cannot read. Its reason tells that there is no Start menu, that `use <item>` uses an item of the Bag, and the items that work now, or that none works.

The answer is JSON: `reason`, `action`, `mission`, `objective` and `note` (200 characters at most each). The rules tell the model to keep its **Mission** until the game shows that it reached it, and to change its **Objective** as often as it needs: a person that is not where the model expected changes the **Objective**, not the **Mission**. An empty `mission` keeps the last one. An action that is `impossible` is not an error: the model sees it in its history. The Bot also reads an action in the form of a call, for all the actions: `press(Up)`, `go(B)`, `buy(POTION, 2)` `goTo(4, 7)` and `use(POTION, SQUIRTLE)` are the same as `press Up`, `go B`, `buy POTION 2`, `goTo 4 7` and `use POTION on SQUIRTLE`. `name` takes the rest of the line as the text, with its spaces and its case: `name Mr Bulb` gives "Mr Bulb", and `name(Bulby, Jr.)` keeps its comma. The prompt teaches the form with spaces.

The Bot reads a comma between the arguments as a space, also with no parentheses: `goTo 9, 42` is `goTo 9 42`, and `buy POTION, 2` is `buy POTION 2`. `name` and `choose` keep their commas. When the Bot cannot read an answer and its first word is an action, the reason gives the form of the action and one example: `"goTo 9 north" is not an action: write goTo <x> <y>, for example goTo 9 42`.

The **Memory tree** replaces the notes that the model wrote again at each call (design: OptMem, https://github.com/rafmyr/OptMem). `note` is one line that the model adds when it learns something, often empty; nobody changes it later. The notes have the numbers 1, 2, 3… A node `#a-b` is the summary of the notes a to b, and `#n` is the note n. When two neighbour nodes have the same size, as in a binary counter, the code makes a **Summary call** at once, at the same **Decision point**: a separate request to the model of the **Run** (JSON schema `summary`) with the texts of the two halves, which gives the summary of their parent node. A node of 2^k notes has a limit of 200 × (k + 1) characters: 200 for a note, 400 for 2 notes, 600 for 4 notes. The schema and the prompt give that limit, and the prompt asks for the newest facts first, in short sentences. When a summary is too long, the code cuts it at the end of its last full sentence that fits, else at the last space: never in a word. Thus 13 notes give the top nodes `#1-8`, `#9-12` and `#13`, and the prompt shows only these. A **Summary call** that failed leaves its node with no summary: the prompt shows the two halves in its place, and the code tries the call again after the next **Model call**. A note that is the same as the last note is not added. The tree comes from the events of the **Run** only (`memoryTree(events)`), so a replay builds it again.

The **Model calls** at the same **Decision point** are one conversation. After `viewAtlas` or `zoom`, after an answer that the Bot cannot read, or after an action that is `impossible` (the player did not move), the next call sends the same system and user messages, then the last answer (`assistant`) and a new user message: the full **Atlas**, the two halves of a node, the error, or the action with the reason of the Harness (after a `goTo` or a `go`, also the exits of the map). After 3 `impossible` actions in a row in one conversation, the next call starts a new conversation. A request that failed adds nothing: the next call sends the same messages again. When the Bot plays an action, the conversation ends, and the next call starts a new one, with a new prompt. Thus the second call of a conversation starts with the full first call, and the providers can take it from their cache.

The **Run** of the model bot continues after each **Milestone**. It ends with `cost limit` (a normal end, with a Run record) when the cost of the **Run** (the sum of `usage.cost` of the **Model calls** and the **Summary calls**) is more than the cost limit: 0.50 $ by default, and `LAB_COST_LIMIT` in `lab/.env` changes the default. It also ends with `user stop`, or with `goal` at `badge-8`. With the option `stopAtWhiteout` (on by default), it ends with `whiteout` when all the Pokémon of the party faint. It has no frame budget and no no-progress limit. The Bot reads the first JSON object of an answer, also after other text (some models write a stray "{" line or a code fence before it). The model bot stops (`bot stopped`, with an error) after 3 answers in a row that it cannot read: an answer with no JSON object, a field that is missing, an action that is not in the list, or a request that failed.

Each **Model call** is a `model` event of the **Run record**: `model` (the id), `situation` (what the game waited for, and where), `prompt` (`system`, `user`, and `turns`: the `assistant` and `user` messages after the first user message of the conversation; a record from before the conversations has no `turns`), `answer` (the text, or `null` when the request failed), `decision` (`reason`, `action`, `mission`, `objective`, `note`, or `null` when the Bot cannot read the answer; a record from before the **Memory tree** has `notes` and no `note`: `readRecord` in `src/harness/record.ts` reads `notes` as `note`; a record from before the **Mission** has no `mission`), `error` (why the Bot cannot read the answer, else `null`), `stuck` and `reflection` (the stuck counter when the conversation of the call started, as its prompt shows it, and true in a reflection turn; a record from before the version 4 has none), `usage` (`promptTokens`, `cachedTokens` (the prompt tokens that the provider read from its cache, from `prompt_tokens_details.cached_tokens` of OpenRouter; a record from before the cache has none), `completionTokens`, `reasoningTokens`, `cost` in $) and `latencyMs`. The header of the record has the model and its options in `bot.model`. A model bot asks its AI model through `harness.modelCall(ask)`: the Harness calls the option `onModelCallStart` of `Harness.open`, runs `ask`, measures the latency, adds the `model` event, calls the option `onModelCall`, and gives back the action of the answer. Each **Summary call** is a `summary` event: `model`, `from` and `to` (the node), `prompt`, `answer`, `summary` (or `null` when the call failed), `error`, `usage` and `latencyMs`. The Bot makes it through `harness.summaryCall(ask)`, which adds the event and calls the option `onSummaryCall`. `modelTotals(events)` (in `src/harness/record.ts`) gives the totals: the number of **Model calls**, and the tokens and the cost of the **Model calls** and the **Summary calls**. At the end, `bun run bot` prints the **Model calls**, the tokens and the cost.

In the tests, a fake model answers: `bun test` never calls the network.

### The stuck counter and the reflection turn

- Progress: a new map, a new **Milestone**, a new exit in the **Atlas**, a level up, or a text of a person that the player did not hear before. A new cell is not progress.
- The stuck counter is `harness.noProgress.stuck`: the **Decision points** since the last progress (see `no progress` in "Run a Bot"). The prompt shows it at each call: "Decision points since your last progress (a new map, a new Milestone, a new exit seen, a level up or a new text of a person): 12." The tries since the last progress start at the same progress.
- A reflection turn is the first walk **Decision point** at 20 on the counter, then at 40, 60… (`REFLECTION_EVERY` in `src/model/decision.ts`). A battle or a choice at 20 moves it to the next walk. It is a normal decision: the same **Model call**, with no separate request.
- Its prompt adds the full **Atlas** after the extract, and the instruction: read the **Memory tree** and the full **Atlas**, use `zoom` freely (`zoom` stays in the same conversation), write a lesson in `note` (what the model tried, why it failed, what it will do now), and set a new `objective`. `viewAtlas` is not an action in a reflection turn. The notes and the **Objective** are the only things that stay after the action: the conversation ends.

### The events that ask for a note

The code compares the game now with the game at the last new conversation, and reads the events of the **Run** since the last **Model call**. For each important event, the prompt has the line "Something important happened: …", and then "Write a note if it can help you later." The model decides if it writes the note. The events:

- a map that the **Run** did not visit before;
- a lost battle (a text of the game says "whited out"; a battle lost with no white-out gives no line);
- a heal: the HP of the party were not all full, and now they are all full, with no battle and no `use` between. The line names the map and the last person that the player talked to (`atlas.lastTalk`);
- an item that was not in the Bag;
- 2 actions or more in a row that were `impossible` (a **Model call** with no action, as `zoom`, does not stop the count).

### The rules for notes

The rules and the description of `note` say: a note is a fact that the game proved, or a lesson (what works, what fails and why). A note is never a guess, and never HP values. The model writes a note after an important event or when it learns a lesson, and never writes the same note again.

### Blocked edges

An edge that the player cannot cross now has a reason in the **Atlas** (`blocked`, see "The Atlas"). Only water exists now: "you cannot go there now: the south edge of PalletTown is water. Only a Pokémon that knows SURF can cross water, and you have none." The extract (in the list of the edges) and the full **Atlas** show this reason, and the edge is not a target of `go`. A `goTo` past the edge gives the same reason as `impossible`, so the prompt and the answer of the Harness agree.

### Fixed obstacles

The cut tree, the rock of ROCK SMASH and the boulder of STRENGTH are objects of the game, as the people, but they never move by themselves. The Harness knows them from their graphics (`CUT_TREE`, `ROCK_SMASH_ROCK`, `PUSHABLE_BOULDER`): they are fixed obstacles, not people. The grid of the map (`grid.kinds`, also the grid of the Atlas) has `#` on their cell, so a route, the targets and the **Atlas** see a wall, and `goTo` never waits for them. When there is no route, but a route through the fixed obstacles exists, `goTo` is `impossible` at once, with no frames: "you cannot go there now: a CUT TREE at ViridianCity (11, 24) blocks the way. Only a Pokémon that knows CUT can remove it". The extract and the full **Atlas** list them with their move and no letter, so `go` never targets them. The Harness cannot use CUT, ROCK SMASH or STRENGTH yet.

## The Run record

After `play`, `harness.record()` gives the **Run record**: the whole Run from frame 0 to now, also the actions before `play`. The Harness keeps it in memory; `bun run bot` writes it, also when the Bot throws an error, to `runs/<bot>-<version>-<date>.json`. `runs/` is not in git. The record has:

- `header`: `parent` for a continued Run (the file name of the record that it continues), the origin of the Run (`rom`: the SHA-256 of the ROM file with the bytes of `BuildDateTime` at zero; `seed`: `gLabRngSeed` in the ROM; `startSave`: the SHA-256 of `saves/start.sav`, or `null` when there is no Starting save), the **Knowledge level**, and the name and version of the Bot (and `model` for a model bot: its AI model and the options). The record has no save data.
- `buttons`: the keys at each frame from frame 0 (the Starting save), compressed: `[keys, frames]` is a set of keys held for that number of frames. The keys are the bits of `Keys` in `src/protocol.ts`.
- `events`, in frame order: `action` (each **Macro-action** and **Raw input**, with its parameters, its result and the frame where the Bot asked for it), `map` (the player arrives on a map), `battle` (`start` or `end`), `milestone` (a new **Milestone**) and `model` (a **Model call** of a model bot: see below). The `frame` of a game event is the frame count after the frame where the Harness saw it. The Harness reads the map and the Milestones only on the overworld and in a battle: the first `map` event is the end of the boot.
- `result`: the result of `play`.

`replay(record)` (in `src/harness/record.ts`) starts a new Run, runs the buttons alone, and gives the `map`, `battle` and `milestone` events, the last frame and the screen hash. The `action` and `model` events come from the Bot, not from the buttons, so a replay does not give them. `replay` does not compare its events with the record: the caller does, as `src/harness/record.test.ts` does. It does not accept a record when the ROM hash, the seed or the Starting save hash is not the same. A rebuild of the same code at the same repo path keeps the ROM hash: the record of the scripted bot replays after `touch src/main.c && make lab` with the same events, frames and screen.

## Continue a Run

A Run can continue a stopped Run: `bun run bot model --continue runs/<file>.json`, or in the Viewer, "continue <file>" in the list of the panel "Runs" before "Start the Bot". `Harness.open({ parent: { name, record } })` replays the buttons of the record at full speed, with no Bot: the Atlas, the battle watch and the Milestones see the same frames and the same actions as in the parent Run. Then the Harness keeps the events of the record, so the model bot has the **Memory tree**, the **Mission** and the texts of the people of the parent Run. It does not open a record with another ROM hash, seed or Starting save hash, or a record whose buttons do not give the same `map`, `battle` and `milestone` events.

The new Run record has the buttons and the events of the parent, then the new ones, and `header.parent`. Its `result` counts the frames and the Raw inputs of the whole Run, from the start of the parent `play`. The model can be another one: each `model` event has its model. The cost limit counts the new **Model calls** and **Summary calls** only; `modelTotals` counts them all, and the panel "Stats" shows the cost of the whole Run and the percentage of the cost limit for the new calls only. The 3 answers in a row that the Bot cannot read, the tries since the last progress and the stuck counter also count from the start of the continuation. With no Knowledge level in the command, the Run takes the level of its parent.

## Replay a Run record in the Viewer

The panel "Replay" of the Viewer lists the files of `runs/` (the list loads when the page opens). "Replay" starts the Run again from the Starting save and runs the buttons of the record at ×1, with sound when the sound is on. The replay has no pauses: the record has no time for the thinking of the Bot (ADR 0002). The Viewer does not start a file that is not a Run record. It also does not start a record with another ROM hash, seed or Starting save hash: then the Run starts again from the Starting save and the keyboard plays it.

While the replay runs, the keyboard does not play, and "Load state (L)" does not load the savestate. Pause and the speeds work. The panel shows:

- the current **Macro-action** or **Raw input**, from the frame where the Bot asked for it. When its frames end, the panel adds its result and its texts.
- for a model Bot: the model, the reasoning and the starter of the record, the **Model calls** and the cost up to the frame of the replay, and the totals of the record with its cost limit. Then the last text of the model (`model` events).
- the events of the record (actions, maps, battles, **Milestones**, model texts), each one at its frame.

The server sends the events of a frame before the screen of that frame. A page that opens during a replay gets the events that it missed. At the end of the record, the game stops at its last frame: the replay of a record of the scripted bot ends at frame 15017 with the same screen as the Run. "Back to the keyboard" ends the replay: the keyboard plays the Run from that frame. "Restart" also ends it. Then the panel clears.

## Runs in parallel

`RunPool` (in `src/harness/pool.ts`) plays up to 4 **Runs** at the same time. Each **Run** plays in its own Bun worker (`src/harness/worker.ts`), with its **Harness** and its **Bot**: a **Macro-action** runs its frames in one synchronous block, so a **Run** in the Viewer process would stop the Viewer. Each **Run** is one emulator. The limit of 4 is a choice: the machine plays about 12 **Runs** at full speed. A pool counts only its own **Runs**: it does not know the emulators of other processes (another Viewer, `bun run bot`, the tests). Do not start them at the same time as a full pool.

- `pool.start({ bot: "model" })` starts the **Bot** `bots/model.ts` in a new worker (`bot` can also be the absolute path of a module, as for `loadBot`), with the options of `Harness.open` (`knowledge`, `frameBudget`, `noProgressLimit`). For a model bot, `model` gives its AI model and the options, all of them (the `model` of the Bot that `loadBot` gives); for another **Bot**, `model` is an error. It throws an error when `limit` **Runs** play (`new RunPool(limit)`, 4 by default). `pool.full` is true when the pool cannot start one more **Run**. A **Run** keeps its place until its worker stops, after the end of the **Run**.
- `run.stop()` asks the worker to end the **Run** with `user stop`, and `run.stopAsked` is then `true`. The worker reads a shared flag (`SharedArrayBuffer`) at each decision of the **Bot**, not a message: a scripted **Bot** gives the event loop of its worker no turn before the end of its **Run**.
- `run.done` gives the **Run record** and the error of the **Bot** (or `null`) when the worker stops; `run.end` has the same value then, and is `null` while the worker plays. When the **Run** cannot start (no such **Bot**, no ROM), the record is `null`.
- While the **Run** plays, `run.view` has its frame, its screen (at most 60 times a second) and its state, map grid, actors, camera and `sight` (`harness.sight()`), at most 10 times a second. `run.events` has the events of the **Run record** up to the end of the last **Macro-action**, **Raw input** or **Model call**, and all of them at the end. `run.modelCallsStarted` counts the **Model calls** that started: a **Model call** runs while its `model` event is not in `run.events`. At the start of each **Model call**, the worker sends the screen and the state of the frozen frame.

A **Run** in a worker gives the same **Run record** as the same **Run** alone: `src/harness/pool.test.ts` plays the scripted bot alone, then 4 times at the same time, and compares the records.

In the **Viewer**, the panel "Runs" starts a **Bot** ("Start the Bot") and lists the **Runs**: the **Run** of the Viewer (keyboard or replay) and the **Runs** of the **Bots**. Select one in the list to show it: the Viewer then shows its screen, its state and its events (in the panel "Replay"). The other **Runs** do not stop. The whole-map view of another map shows the people of the **Run** of the Viewer only: for a **Run** of a **Bot**, it shows none. The **Run** of the Viewer is one of the 4 emulators, so the Viewer starts 3 **Runs** of **Bots** at most at the same time. A **Run** of a **Bot** plays at full speed, with no sound. The keyboard, the speeds, pause and the savestate act only on the **Run** of the Viewer: while a **Run** of a **Bot** is shown, the server ignores them and the keyboard does not play. At the end of a **Run** of a **Bot**, the Viewer writes its **Run record** to `runs/`. "Replay" shows the **Run** of the Viewer again.

For the model bot, the panel "Runs" has a field for the OpenRouter model id, a field for the cost limit in $, a list for the reasoning (`low` by default), a list for the starter (`free` by default), a box "stop at a whiteout" (on by default) and a list for the start: the Starting save, or "continue" a Run record of `runs/` (see "Continue a Run"). The list of the Runs names the record that a Run continues. Empty fields take the defaults. "Stop the Run" stops the shown **Run** of a **Bot** (`user stop`, with a **Run record**): for a model bot, after the **Model call** that runs, so it can take some seconds. Until the end, the list shows "stops…". Under the list, the panel shows the model of the shown **Run**, its reasoning, its starter and its cost now, with its cost limit. In the panel "Replay", "the model thinks…" shows while a **Model call** runs. When the answer comes, the panel shows the **Mission**, the **Objective** and the reason with the action, before the action plays. A replay of a **Run record** shows them too, at the frame of each **Model call**.

The panel "Model", under the Lab, lists the **Model calls** of the shown **Run** (frame, situation, action, the stuck counter, and "reflection turn" in color) and shows one of them in full: the answer (action, reason, **Mission**, **Objective**, note, or why the Bot cannot read it), the tokens with the cached tokens, the cost and the latency, then all the messages of the call in blocks: the first user message (progress, memory, situation and tries, history, important events, party, local view, people, **Atlas**, targets, battle, question, actions), then for each turn of the conversation the last answer ("Your answer") and the new user message (full **Atlas**, zoom, error, request), then the rules (the system message). A block with no known title is "Other". It follows the last call; a click on a call in the list shows that call, and "Follow the last call" follows again. It reads only the `model` events, so it works live and in a replay. In a replay, the calls of one conversation come at the same frame, so they show together.

The panel "Stats", under the panel "Model", shows the shown **Run** as lanes on one axis of frames (plain SVG, no chart library), in this order:

- Milestones: one band for each chapter, from a **Milestone** to the next one ("→ next Milestone" for the open chapter), and a dashed rule at each **Milestone** through all the lanes.
- Areas: two rows. The top row is the **Area**, one block while the player stays in it, with its name of the game in normal case ("Viridian City"). The bottom row is the map: an inside map (not a town or a route in the game data) has a lighter color of its **Area** (mixed with white) and its name without the **Area** name ("Prof. Oak's Lab", "Poké Mart", "Room 1" for `FiveIsland_LostCave_Room1`); a town or a route is a faint block with no name. The color of an **Area** is the order of its first visit in the **Run** (8 colors).
- Cost: the cost so far, as steps. When the cost is less than half of the cost limit, the scale stops at the cost; when it is more, the limit is a dashed red line. At the left: the limit and the percentage used.
- Stuck: the **Stuck counter** of each **Model call**, held until the next call: green under 1/3 of the **Reflection turn** interval (`REFLECTION_EVERY` in `src/model/decision.ts`), orange under 2/3, red above. A dashed violet line shows the interval, and a violet mark shows each **Reflection turn**. At the left: the counter now and the maximum.
- Prompt tokens: the prompt tokens of each **Model call** (from its usage), as a blue line with one dot for each call. At the left: the tokens of the last call and the maximum. A call with no prompt tokens (a request that failed) has no dot.
- Model calls: one tick for each call; an answer that the Bot cannot read is a tall red tick.
- Played actions: one tick for each **Macro-action** or **Raw input**, by result: `done` short and green, `interrupted` blue, `blocked` orange, `impossible` tall and red.
- Summary calls: one violet tick for each **Summary call**.
- Battles: one orange bar for each battle.

Live, the axis goes from 0 to the frame of now. In a replay, it goes to the end of the **Run record** (the frames of its buttons), and the frames that are not played yet are grey. A **Run** with no **Model call** and no model settings (a scripted bot) has no lanes Cost, Stuck, Prompt tokens, Model calls and Summary calls; a model bot has them also before its first call. A **Run record** of a model bot before version 4 has no **Stuck counter**: the lane Stuck shows a sentence. A **Run record** with no prompt tokens shows an empty lane Prompt tokens with a sentence. A **Continued Run** has a violet rule "continued here" at its first frame. Its percentage of the cost limit and its limit line count only its own **Model calls** and **Summary calls**: the limit line is the limit above the cost of the parent. When the replay or the Run starts, the server reads the first frame and the number of events of the parent in the parent **Run record** (`header.parent`), and sends them in the status.

A drag on the lanes selects a range of frames. A click selects one **Model call**: from its frame to the frame before the next call, with the actions that it played (and the other calls of the same **Decision point**). Esc or "select all" selects the whole **Run**. A range stays the same while a live **Run** continues; the selection is cleared when the Viewer shows another **Run** or another replay. While the mouse drags, the panel does not draw again. The line under the lanes follows the mouse: the frame and its time, the cost so far, the **Stuck counter**, the **Area** and the map, and, near the mouse (6 pixels), the nearest call and at most 3 actions that are not `done`. Under it, a summary of the selection (its range, calls, cost, played actions, `impossible` actions, unreadable answers, **Summary calls**, new notes of the **Memory tree**, the **Stuck counter** at the end and its maximum, the **Reflection turns**, and the smallest and the largest prompt of its **Model calls** in tokens) and three cards: the actions that the model chose (the actions never chosen at the end, dashed), the reasons of the `impossible` actions and of the unreadable answers (grouped when only the numbers are different), and each **Model call** with the actions that it played under it.

The **Areas** come from the game data, not from the **Run record**: at start, the server reads `region_map_section` in each `data/maps/*/map.json` and the names in `src/data/region_map/region_map_sections.json` (`readAreas()` in `src/game.ts`), with the map type, and makes the name of each inside map. It sends the Viewer one table map → **Area** and inside name. So old **Run records** also get **Areas**. The panel reads the events, this table and the status (the frame, the cost limit, the end of the replay and the continuation), so it shows the same stats live and in a replay at the same frame. The list of the actions is `MODEL_ACTION_NAMES` in `src/model/decision.ts`: the type check fails when an action of the model bot is not in it.

The panel "Memory tree", under the panel "Stats", shows the **Memory tree** of the shown **Run** from its events, live and in a replay at the same frame. On the left: the top nodes as the prompt shows them; a click on a node opens its two halves, down to the notes (as `zoom`). On the right: the **Summary calls**, the newest first, with the frame, the node, the summary or the error, the cost and the time; a click on a result opens the prompt and the answer.

The whole-map view shows in grey the cells that the player of the shown **Run** never saw (`harness.sight()`; for the **Run** of the Viewer, the server watches its frames from the Starting save). A load of the savestate keeps the cells that the player saw after the save: the player saw them. A map that the player never visited is all grey.

## The Doc tab

The Viewer has two tabs: "Lab" (the screen, the panels and the whole-map view) and "Doc". The Doc is one page that tells what the lab can do now: the principle, what the harness can do and cannot do yet, and the **Bots**. Its text is in `viewer/index.html`, and a person writes it by hand: this README stays the full reference. A tab only shows or hides a part of the page, so a change of tab does not stop the **Run** of the Viewer or the **Runs** of the **Bots**. In the Doc tab, the keyboard does not play: the arrow keys scroll the page.

The list of the **Bots** in the Doc and in the panel "Runs" comes from the server: `botInfos()` (in `src/harness/harness.ts`) loads each module of `bots/` and gives its name (the name of the module), the kind of its **Bot** (`model` for a **Bot** with `model`, else `scripted`), its version and its goal. When a module gives no **Bot** (it throws an error, or a model bot has a bad option), the Doc shows the error for that module, and the other **Bots** stay in the two lists. The scripted bot is not in `bots/`, so the two lists do not show it.

`viewer/doc.test.ts` fails when the table of the **Macro-actions** in the Doc does not have one line for each **Macro-action** of the harness, or when the Doc does not name the **Raw input** `press`. The harness gives its **Macro-actions** in `MACRO_ACTIONS`: the names in `ACCEPTS`, the map from each kind of `waitingFor` to the **Macro-actions** that it accepts. When you add a **Macro-action**, add its line to the table of the Doc.

## Make the Starting save

1. Start the Viewer with no `saves/start.sav`. The lab build then starts as the vanilla game: intro, title screen, new game.
2. Play to your room and set the text speed to "Fast" in the options.
3. Save in the game. Wait for the message that tells you the save is complete.
4. Click "Write the Starting save". The harness writes `saves/start.sav` and keeps the previous file next to it.

With `saves/start.sav`, the lab build skips the intro, the title screen and the "Previously on your quest" recap, and continues the game in a few frames.

## Files

- `shim/shim.c`: plain C functions over the libmgba core.
- `src/core.ts`: one emulator instance (bun:ffi).
- `src/symbols.ts`: reads the debug info of the `.elf` (addresses and types of all globals, function addresses). Cached in `.cache/`.
- `src/memory.ts`: typed memory reads, for example `mem.global("gSaveBlock1Ptr").deref().field("pos").field("x").int()`.
- `src/game.ts`: FireRed state (map, party, badges, money, context, **Milestones**), what the game waits for (walk, text, choice, the battle menus, the naming screen), the grid of the player's map or of any map from ROM, the actors on it (people, fixed obstacles, trainer sight, triggers), and the **Interruption** of each frame (battle, trigger, trainer, script).
- `src/prompts.ts`: the text decoder, the message boxes and their text, the window of the whiteout text, and the yes/no.
- `src/battle.ts`: the battle: the kind, the player's and the enemy's Pokémon from the battle data, the enemy as the player sees it, the battle menus and their cursors, the yes/no of the battle scripts, the order of the party in the party menu of a battle, and the moves that the enemy used.
- `src/menus.ts`: the Start menu and the party menu: their items, their cursors, and the text of the party menu when the game refuses a Pokémon. The menus of the scripts: the `multichoice` menus and the grid menu `multichoicegrid` (the blackboard of the school), with their options, their cursor and their columns. The naming screen: what it names, its keyboard pages, its cursor and its text.
- `src/shop.ts`: the Poké Mart: the shop menu BUY, SELL, SEE YA! and the buy list, each with the items for sale and their prices, and the quantity box, the yes/no and the end of a buy or a sale.
- `src/bag.ts`: the Bag: its pockets and items from the save block, the name, the effect, the battle use and the walk use of each item from `gItems`, the items that work now, the items that a Poké Mart buys, the Bag menu (its list and the menu of an item) and the animation of an item on a Pokémon after a walk use.
- `src/party.ts`: the party, as the Summary screen shows it: species, ability, held item, nature, EXP and moves from the encrypted Pokémon data, with the types, the move data and the texts from the ROM tables, and level, HP, stats and status from the party fields.
- `src/run.ts`: one **Run**: the emulator and the game reads, started from the **Starting save**, and `readState()`, the state that the Viewer shows.
- `src/server.ts`: the Viewer page and its WebSocket, the wall-clock pacing of the Run, the replay of a **Run record**, and the **Runs** of the pool that the Viewer starts and shows.
- `src/model/`: the parts of the model bot: `openrouter.ts` (the settings and the request), `decision.ts` (the answer and its action), `targets.ts` (the targets of a walk), `extract.ts` (the extract of the **Atlas** and the full **Atlas** in text), `prompt.ts` (the text of the prompt, with the tries since the last progress) and `important-events.ts` (the events that ask for a note).
- `src/harness/`: the API of the **Bot**: `harness.ts` (observation, **Macro-actions**, **Raw inputs**, the end of a **Run**, and the loading of a **Bot** from `bots/`), `menu-driver.ts` (the keys of the battle menus, the Bag, the Poké Mart and the party menu), `path.ts` (A* over the maps: walk, ledges, warps and map edges), `atlas.ts` (the **Atlas** and the sight of a **Run**), `record.ts` (the **Run record**, `RecordPlayer` that gives its keys and its events frame by frame, and its replay), `pool.ts` (up to 4 **Runs** in workers) and `worker.ts` (one **Run** of the pool), `play.ts` (the `bot` command).
- `HISTORY.md`: the steps of the lab, in order (the plan of a video). Add a step at the end of each piece of work.
- `bots/`: the **Bots**: `model.ts` (the model bot). The scripted bot of the tests is `src/harness/scripted-bot.ts`.
- `viewer/`: the page. `viewer/mapdraw.ts` draws a map at any scale (screen overlay and whole-map view); `viewer/audio.ts` plays the sound; `viewer/replay.ts` is the replay panel; `viewer/runs.ts` is the panel of the **Runs**; `viewer/dom.ts` has the DOM builders that the panels share; `viewer/model-panel.ts` is the panel "Model"; `viewer/stats-panel.ts` is the panel "Stats" (its data and its selection), and `viewer/stats-lanes.ts` draws its lanes; `viewer/memory-panel.ts` is the panel "Memory tree"; `viewer/doc.ts` is the tabs and the list of the **Bots** in the Doc. All the texts of the Viewer are in English.

## Sound

The sound plays only at speed ×1. It is off when the page opens: `M` or the button "Sound" turns it on and off. The page keeps about 60 ms of audio queued and sends the queue length to the harness, which makes the Run up to 1% faster or slower to hold it there (the emulator clock and the sound card clock drift apart).

## Notes

- The ROM bytes change on each build: the game stores the build date (`BuildDateTime`). To compare two builds, ignore those bytes.
- The vanilla build is compiled without `-g`, because `-g` changes the order of linker veneers in the ROM.
- `saves/`, `runs/` and `.cache/` are not in git. Never put a ROM in git or on a public URL.
